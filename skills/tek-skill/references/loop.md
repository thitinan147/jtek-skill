# ลูป card — เวอร์ชัน 12

กติกานี้เป็นของ skill `tek-skill` ไม่ได้ copy เข้า repo ที่เปิดอยู่

ลูปอยู่ที่ repo ที่เปิดอยู่ตัวเดียว เอเจนต์ไม่ไปเปิด repo อื่น

คนเขียน card และเปลี่ยนคำบนบรรทัด คนเรียก `/tek-send-back` `/tek-mark-merge` `/tek-mark-close` เอง เอเจนต์ไม่เรียกสามคำสั่งนั้น

| `/tek-open-review` | เปิดของที่ `รอรีวิว:` เทียบหัว **ตรวจผ่านเมื่อ** ไม่เปลี่ยนบรรทัด |
| `/tek-send-back` | เปลี่ยน `รอรีวิว:` เป็น `ส่งกลับ:` |

## ไฟล์ใน repo ที่เปิดอยู่

- `card-loop/board.md` = คิว คำบนบรรทัดคือสถานะเดียว และตารางคำสั่งเทสของ repo นี้
- `card-loop/backlog/<id>.md` = card ที่คนเขียน
- `card-loop/plan/<id>.md` = โน้ตลงมือของเอเจนต์ และตาราง **การตัดสินใจ** ที่คนอ่านตอน `/tek-open-review`

อ่านตารางใน `card-loop/board.md` ก่อนลงมือ `<STACK_LOCK>` ต้องมีอย่างน้อยภาษา เฟรมเวิร์ก คำสั่งเทสหรือชนิดตรวจ และของที่ห้ามใช้ใน repo นี้ ใบที่เปิดได้มีแค่ชื่อใน `<TEK_SKILLS>` กับ `<REPO_SKILLS>` ตาม [skills.md](skills.md)

ทุกครั้งที่เลือกทาง หยุดเพื่อ `ถาม:` หรือผ่านหลักฐาน ให้เติมหนึ่งแถวในตาราง **การตัดสินใจ** ของ plan: ตัดสินอะไร ทำไม หลักฐานเป็น path หรือคำสั่งเทสหรือ commit

สถานะที่เชื่อมีแค่คำบนบรรทัด คือ `ถาม:` `รอรีวิว:` `ส่งกลับ:` `merge:` และ `ปิด:`

```text
คนเขียน card
    → เอเจนต์ทำ /tek-do-card
        เจตนายังไม่ปิด → เขียน ถาม ที่ card และบรรทัด board → ไม่เปิดของให้ review
        เจตนาปิดแล้ว → ลงมือบน branch → เก็บผลเทสและหลักฐานบนพื้นผิว
            ย้อนกลับไม่ได้ หรือครบ 3 รอบแล้วยังไม่ผ่าน → เขียน ถาม → ไม่ขอ review
            ผ่าน → เปิดของให้ review แล้วตั้งบรรทัดเป็น รอรีวิว
                คนเรียก /tek-open-review
                    รับ → /tek-mark-merge
                    ไม่ครบ → /tek-send-back
                    ไม่เอา → /tek-mark-close
```

## กติกา

- หนึ่งข้อที่กำลังทำมีได้ข้อเดียว ก่อนหยิบข้อใหม่ให้อ่านคำบนบรรทัดตามขั้นหยิบ
- ข้อที่บรรทัดเป็น `ส่งกลับ:` ทำต่อของเดิม ไม่เปิดของใหม่ให้ review พอหลักฐานผ่านให้เปลี่ยนบรรทัดเป็น `รอรีวิว:` แล้วหยุด
- เจตนาไม่ปิด งานย้อนกลับไม่ได้ หรือครบ 3 รอบแล้วยังไม่ผ่านหลักฐาน → เขียน `ถาม:` ทั้งท้าย card และท้ายบรรทัด แล้วหยุด
- เปิดของให้ review ได้เมื่อหลักฐานครบ เทสที่เกี่ยวข้องเขียว และ diff อยู่ในหัว **ทำ** / **ไม่ทำ**
- เอเจนต์ไม่ติ๊ก `merge:` หรือ `ปิด:` และไม่ merge สาขาหลัก
- ยังไม่ push สาขาหลักจนกว่าคนจะเรียก `/tek-mark-merge`
- อย่าใส่ trailer ของโมเดลใน commit

### เจตนาปิดแล้ว

card มีชนิดเดียว ทางเดียว และหัว **ทำ** **ไม่ทำ** **ตรวจผ่านเมื่อ** อ่านแล้วลงมือได้โดยไม่ต้องเลือกแทนคน

ยังไม่ปิดเมื่อขอบเขตคลุมเครือ มีสองทางที่ผลไม่เท่ากัน จะลบของที่อาจยังมีคนใช้โดย card ยังไม่เลือก หรือจะเปลี่ยนสัญญาที่คนอื่นเรียกโดย card ยังไม่เลือก

### งานที่ย้อนกลับไม่ได้

หยุด เขียน `ถาม:` ที่ card และบรรทัด ห้ามลงมือต่อเมื่อจะลบข้อมูล production, force-push, ส่งข้อความหรือของออกนอก repo, หรือ merge สาขาหลัก

push branch ของข้อเพื่อเปิดของให้ review ทำได้

### เกณฑ์ 3 รอบ

หนึ่งรอบคือพยายามทั้งชุดจนจบครั้งหนึ่ง หลักฐานคือเทสที่เกี่ยวข้องเขียว และถ้าเป็น `fix` ที่ผู้ใช้เห็นจอ ขั้นตอนเดิมบนพื้นผิวเดิมไม่เกิดบั๊ก

เริ่มที่ `รอบหลักฐาน` = 1 ใน plan พยายามทั้งชุดแล้วยังไม่ผ่าน ให้ดูค่าปัจจุบันก่อน ถ้าน้อยกว่า 3 ให้บวก 1 แล้วพยายามใหม่ ถ้าค่าเป็น 3 อยู่แล้วและยังไม่ผ่าน → `ถาม:` ที่ card และที่บรรทัด ห้ามขอ review เทสแดงที่ตั้งใจก่อนลงมือไม่นับเป็นรอบที่ล้ม

คนเรียก `/tek-send-back` คือคำขอใหม่ ครั้งแรกที่เอเจนต์เห็นให้ตั้ง `รอบหลักฐาน` เป็น 1 และตั้ง `สถานะรอบ` ใน plan เป็น `ส่งกลับ` ถ้า plan เป็น `ส่งกลับ` อยู่แล้ว ห้ามรีเซ็ตซ้ำ

หลักฐานผ่านขณะบรรทัดเป็น `ส่งกลับ:` ให้เปลี่ยนบรรทัดเป็น `รอรีวิว:` ตั้ง `สถานะรอบ` เป็น `รอรีวิว` commit ที่ `card-loop/` แล้วหยุด

นับรอบจากช่อง `รอบหลักฐาน` ใน plan เท่านั้น

### ถาม

วางท้าย card และต่อท้ายบรรทัดด้วย `ถาม:` โดยข้อยังเป็น `- [ ]` แล้ว commit บรรทัดนั้นที่ `card-loop/` แล้วหยุด

```markdown
ถาม: <หนึ่งคำถาม>
ทำไมถึงไปต่อไม่ได้: …
ทางที่เห็น: A … / B …
```

คนตอบด้วยการล้างหัว **ถาม** ใน card และแก้ card จนเจตนาปิด ไม่ต้องแก้บรรทัด

เอเจนต์เห็นหัว **ถาม** ว่างและเจตนาปิดแล้ว จึงลบ `ถาม:` ออกจากบรรทัด commit ที่ `card-loop/` แล้วทำข้อนั้นต่อได้

## ชนิดตั๋ว

หนึ่งค่า จากชุดที่ Conventional Commits อนุญาต และที่ `@commitlint/config-conventional` ใช้

| ชนิด | ความหมาย | หลักฐานก่อนเปิดของให้ review |
|---|---|---|
| `feat` | พฤติกรรมหรือ interface ใหม่ | เทสของพฤติกรรมนั้นเขียว ด้วย `<TEST_CMD>` หรือคำสั่งที่หัว **ตรวจผ่านเมื่อ** เขียนไว้ |
| `fix` | บั๊กที่พฤติกรรมพัง | เทสของพฤติกรรมนั้นเขียว ด้วย `<TEST_CMD>` หรือคำสั่งที่หัว **ตรวจผ่านเมื่อ** เขียนไว้ |
| `docs` | เอกสารอย่างเดียว | ไม่แตะโค้ดผลิต |
| `style` | จัดรูปแบบ ความหมายของโค้ดไม่เปลี่ยน | ชุดเดิมผ่าน |
| `refactor` | ไม่แก้บั๊กและไม่เพิ่มพฤติกรรม รวมการลบของที่ไม่มีคนใช้ | ชุดเดิมผ่าน |
| `perf` | ทำให้เร็วขึ้น พฤติกรรมผู้ใช้เท่าเดิม | ชุดเดิมผ่าน |
| `test` | เพิ่มหรือแก้เทส | เทสที่เพิ่มเขียว โดยไม่เปลี่ยนพฤติกรรมผลิตเพื่อให้ผ่าน |
| `build` | ระบบ build หรือ dependency | ชุดเดิมผ่าน |
| `ci` | สคริปต์ CI | ชุดเดิมผ่าน |
| `chore` | งานอื่นที่ไม่ได้เปลี่ยนซอร์สหรือเทส | ชุดเดิมผ่าน |
| `revert` | ย้อน commit เดิม | หลังย้อน ชุดเดิมผ่าน |

`fix` ที่ผู้ใช้เห็นจอ ทำให้บั๊กเกิดบนพื้นผิวเดิมก่อนลงมือ แล้วทำขั้นตอนเดิมหลังแก้จนไม่เกิด เทสเขียวแต่พื้นผิวยังเป็นบั๊ก เปิดให้ review ไม่ได้

`<BROWSER_TOOL>` ว่าง และหัว **ตรวจผ่านเมื่อ** ไม่ได้เขียนวิธีตรวจพื้นผิว คือเจตนายังไม่ปิด เขียน `ถาม:` ขอวิธีตรวจ

`<TEST_CMD>` ว่าง และ card ของ `feat` หรือ `fix` ไม่ได้เขียนคำสั่งเทสไว้ในหัว **ตรวจผ่านเมื่อ** คือเจตนายังไม่ปิด เขียน `ถาม:` ขอคำสั่งเทส

ชนิดอื่นเมื่อ `<TEST_CMD>` ว่าง เขียนในของที่เปิดให้ review ว่าไม่มีชุดเทสได้

ชื่อเทสตาม scenario หรือพฤติกรรม

### มาตรฐาน commit

```text
<ชนิด>(<id>): <สรุป>
```

`<ชนิด>` ตรงชนิดของ card `<id>` ตรงชื่อไฟล์ card `<สรุป>` ภาษาอังกฤษ รูปคำสั่ง ปัจจุบัน ไม่ขึ้นต้นด้วยตัวใหญ่ ไม่มีจุดท้าย

บรรทัดว่างแล้วตามด้วยเหตุผลหนึ่งประโยค ยกเว้นชนิด `docs` หนึ่ง commit หนึ่งชนิด งานนอกคิวไม่มี `<id>` ถ้าจะอยู่ในลูปให้มี card ก่อน

## ขั้นตอนของแต่ละคำสั่ง

ขั้นตอนที่ทำให้คำสั่งจบอยู่ใน `SKILL.md` ของคำสั่งนั้น อ่านกติการ่วมด้านบนเฉพาะหัวที่คำสั่งนั้นชี้

คนเรียก `/tek-open-review` ก่อนตัดสิน ตาราง **การตัดสินใจ** ว่างหรือ diff ไม่ตรง card คือหลักฐานไม่ครบ ห้ามติ๊ก `merge:`
