# ลูป card — เวอร์ชัน 10

กติกานี้เป็นของ skill `tek-skill` ไม่ได้ copy เข้า repo ที่เปิดอยู่

ลูปอยู่ที่ repo ที่เปิดอยู่ตัวเดียว เอเจนต์ไม่ไปเปิด repo อื่น

คนเขียน card และเปลี่ยนคำบนบรรทัด คนเรียก `/tek-send-back` `/tek-mark-merge` `/tek-mark-close` เอง เอเจนต์ไม่เรียกสามคำสั่งนั้น

## ไฟล์ใน repo ที่เปิดอยู่

- `card-loop/board.md` = คิว คำบนบรรทัดคือสถานะเดียว และตารางคำสั่งเทสของ repo นี้
- `card-loop/backlog/<id>.md` = card ที่คนเขียน
- `card-loop/plan/<id>.md` = โน้ตลงมือของเอเจนต์ คนไม่รับแผนก่อนเปิดของให้ review

อ่านตารางใน `card-loop/board.md` ก่อนเปิด skill ที่พูดถึงภาษา เฟรมเวิร์ก ไลบรารี หรือโฮสต์คลาวด์ `<STACK_LOCK>` ต้องมีอย่างน้อยภาษา เฟรมเวิร์ก คำสั่งเทสหรือชนิดตรวจ และของที่ห้ามใช้ใน repo นี้

สถานะที่เชื่อมีแค่คำบนบรรทัด คือ `ถาม:` `รอรีวิว:` `ส่งกลับ:` `merge:` และ `ปิด:`

```text
คนเขียน card
    → เอเจนต์ทำ /tek-do-card
        เจตนายังไม่ปิด → เขียน ถาม ที่ card และบรรทัด board → ไม่เปิดของให้ review
        เจตนาปิดแล้ว → ลงมือบน branch → เก็บผลเทสและหลักฐานบนพื้นผิว
            ย้อนกลับไม่ได้ หรือครบ 3 รอบแล้วยังไม่ผ่าน → เขียน ถาม → ไม่ขอ review
            ผ่าน → เปิดของให้ review แล้วตั้งบรรทัดเป็น รอรีวิว
                คนเรียก /tek-open-review
                    รับ → /tek-mark-merge
                    ไม่ครบ → /tek-send-back
                    ไม่เอา → /tek-mark-close
```

## กติกา

- หนึ่งข้อที่กำลังทำมีได้ข้อเดียว ก่อนหยิบข้อใหม่ให้อ่านคำบนบรรทัดตามขั้นหยิบ
- ข้อที่บรรทัดเป็น `ส่งกลับ:` ทำต่อของเดิม ไม่เปิดของใหม่ให้ review พอหลักฐานผ่านให้เปลี่ยนบรรทัดเป็น `รอรีวิว:` แล้วหยุด
- เจตนาไม่ปิด งานย้อนกลับไม่ได้ หรือครบ 3 รอบแล้วยังไม่ผ่านหลักฐาน → เขียน `ถาม:` ทั้งท้าย card และท้ายบรรทัด แล้วหยุด
- เปิดของให้ review ได้เมื่อหลักฐานครบ เทสที่เกี่ยวข้องเขียว และ diff อยู่ในหัว **ทำ** / **ไม่ทำ**
- เอเจนต์ไม่ติ๊ก `merge:` หรือ `ปิด:` และไม่ merge สาขาหลัก
- ยังไม่ push สาขาหลักจนกว่าคนจะเรียก `/tek-mark-merge`
- อย่าใส่ trailer ของโมเดลใน commit

### เจตนาปิดแล้ว

card มีชนิดเดียว ทางเดียว และหัว **ทำ** **ไม่ทำ** **ตรวจผ่านเมื่อ** อ่านแล้วลงมือได้โดยไม่ต้องเลือกแทนคน

ยังไม่ปิดเมื่อขอบเขตคลุมเครือ มีสองทางที่ผลไม่เท่ากัน จะลบของที่อาจยังมีคนใช้โดย card ยังไม่เลือก หรือจะเปลี่ยนสัญญาที่คนอื่นเรียกโดย card ยังไม่เลือก

### งานที่ย้อนกลับไม่ได้

หยุด เขียน `ถาม:` ที่ card และบรรทัด ห้ามลงมือต่อเมื่อจะลบข้อมูล production, force-push, ส่งข้อความหรือของออกนอก repo, หรือ merge สาขาหลัก

push branch ของข้อเพื่อเปิดของให้ review ทำได้

### เกณฑ์ 3 รอบ

หนึ่งรอบคือพยายามทั้งชุดจนจบครั้งหนึ่ง หลักฐานคือเทสที่เกี่ยวข้องเขียว และถ้าเป็น `fix` ที่ผู้ใช้เห็นจอ ขั้นตอนเดิมบนพื้นผิวเดิมไม่เกิดบั๊ก

เริ่มที่ `รอบหลักฐาน` = 1 ใน plan พยายามทั้งชุดแล้วยังไม่ผ่าน ให้ดูค่าปัจจุบันก่อน ถ้าน้อยกว่า 3 ให้บวก 1 แล้วพยายามใหม่ ถ้าค่าเป็น 3 อยู่แล้วและยังไม่ผ่าน → `ถาม:` ที่ card และที่บรรทัด ห้ามขอ review เทสแดงที่ตั้งใจก่อนลงมือไม่นับเป็นรอบที่ล้ม

คนเรียก `/tek-send-back` คือคำขอใหม่ ครั้งแรกที่เอเจนต์เห็นให้ตั้ง `รอบหลักฐาน` เป็น 1 และตั้ง `สถานะรอบ` ใน plan เป็น `ส่งกลับ` ถ้า plan เป็น `ส่งกลับ` อยู่แล้ว ห้ามรีเซ็ตซ้ำ

หลักฐานผ่านขณะบรรทัดเป็น `ส่งกลับ:` ให้เปลี่ยนบรรทัดเป็น `รอรีวิว:` ตั้ง `สถานะรอบ` เป็น `รอรีวิว` commit ที่ `card-loop/` แล้วหยุด

นับรอบจากช่อง `รอบหลักฐาน` ใน plan เท่านั้น

### ถาม

วางท้าย card และต่อท้ายบรรทัดด้วย `ถาม:` โดยข้อยังเป็น `- [ ]` แล้ว commit บรรทัดนั้นที่ `card-loop/` แล้วหยุด

```markdown
ถาม: <หนึ่งคำถาม>
ทำไมถึงไปต่อไม่ได้: …
ทางที่เห็น: A … / B …
```

คนตอบด้วยการล้างหัว **ถาม** ใน card และแก้ card จนเจตนาปิด ไม่ต้องแก้บรรทัด

เอเจนต์เห็นหัว **ถาม** ว่างและเจตนาปิดแล้ว จึงลบ `ถาม:` ออกจากบรรทัด commit ที่ `card-loop/` แล้วทำข้อนั้นต่อได้

## ชนิดตั๋ว

หนึ่งค่า จากชุดที่ Conventional Commits อนุญาต และที่ `@commitlint/config-conventional` ใช้

| ชนิด | ความหมาย | หลักฐานก่อนเปิดของให้ review |
|---|---|---|
| `feat` | พฤติกรรมหรือ interface ใหม่ | เทสของพฤติกรรมนั้นเขียว ด้วย `<TEST_CMD>` หรือคำสั่งที่หัว **ตรวจผ่านเมื่อ** เขียนไว้ |
| `fix` | บั๊กที่พฤติกรรมพัง | เทสของพฤติกรรมนั้นเขียว ด้วย `<TEST_CMD>` หรือคำสั่งที่หัว **ตรวจผ่านเมื่อ** เขียนไว้ |
| `docs` | เอกสารอย่างเดียว | ไม่แตะโค้ดผลิต |
| `style` | จัดรูปแบบ ความหมายของโค้ดไม่เปลี่ยน | ชุดเดิมผ่าน |
| `refactor` | ไม่แก้บั๊กและไม่เพิ่มพฤติกรรม รวมการลบของที่ไม่มีคนใช้ | ชุดเดิมผ่าน |
| `perf` | ทำให้เร็วขึ้น พฤติกรรมผู้ใช้เท่าเดิม | ชุดเดิมผ่าน |
| `test` | เพิ่มหรือแก้เทส | เทสที่เพิ่มเขียว โดยไม่เปลี่ยนพฤติกรรมผลิตเพื่อให้ผ่าน |
| `build` | ระบบ build หรือ dependency | ชุดเดิมผ่าน |
| `ci` | สคริปต์ CI | ชุดเดิมผ่าน |
| `chore` | งานอื่นที่ไม่ได้เปลี่ยนซอร์สหรือเทส | ชุดเดิมผ่าน |
| `revert` | ย้อน commit เดิม | หลังย้อน ชุดเดิมผ่าน |

`fix` ที่ผู้ใช้เห็นจอ ทำให้บั๊กเกิดบนพื้นผิวเดิมก่อนลงมือ แล้วทำขั้นตอนเดิมหลังแก้จนไม่เกิด เทสเขียวแต่พื้นผิวยังเป็นบั๊ก เปิดให้ review ไม่ได้

`<BROWSER_TOOL>` ว่าง และหัว **ตรวจผ่านเมื่อ** ไม่ได้เขียนวิธีตรวจพื้นผิว คือเจตนายังไม่ปิด เขียน `ถาม:` ขอวิธีตรวจ

`<TEST_CMD>` ว่าง และ card ของ `feat` หรือ `fix` ไม่ได้เขียนคำสั่งเทสไว้ในหัว **ตรวจผ่านเมื่อ** คือเจตนายังไม่ปิด เขียน `ถาม:` ขอคำสั่งเทส

ชนิดอื่นเมื่อ `<TEST_CMD>` ว่าง เขียนในของที่เปิดให้ review ว่าไม่มีชุดเทสได้

ชื่อเทสตาม scenario หรือพฤติกรรม

### มาตรฐาน commit

```text
<ชนิด>(<id>): <สรุป>
```

`<ชนิด>` ตรงชนิดของ card `<id>` ตรงชื่อไฟล์ card `<สรุป>` ภาษาอังกฤษ รูปคำสั่ง ปัจจุบัน ไม่ขึ้นต้นด้วยตัวใหญ่ ไม่มีจุดท้าย

บรรทัดว่างแล้วตามด้วยเหตุผลหนึ่งประโยค ยกเว้นชนิด `docs` หนึ่ง commit หนึ่งชนิด งานนอกคิวไม่มี `<id>` ถ้าจะอยู่ในลูปให้มี card ก่อน

## `/tek-setup-board`

ถ้ายังไม่มี `card-loop/board.md` ให้ copy [assets/board.template.md](../assets/board.template.md) ไปที่นั่น แล้วหยุดให้คนเติมตาราง ตารางว่าง ห้ามเรียก `/tek-do-card`

## `/tek-add-card`

คนเขียน card เอเจนต์ไม่เขียนหัว **ทำ** **ไม่ทำ** **ตรวจผ่านเมื่อ** แทนคน

1. ถ้ารหัสข้อไม่ได้มาพร้อมคำสั่ง ให้ถามรหัส
2. ถามว่าบรรทัดไปอยู่ **ทำก่อน** **งานหลัก** หรือ **เก็บเล็ก**
3. copy [assets/card.template.md](../assets/card.template.md) ไปที่ `card-loop/backlog/<id>.md`
4. ใส่บรรทัด `- [ ]` บน board ในหัวข้อที่คนเลือก ข้อยังไม่มีข้อความข้อตกลงให้คนเติมในไฟล์ card

## `/tek-read-board`

อ่าน `card-loop/board.md` แล้วบอกข้อถัดไปตามขั้นหยิบ ข้อที่เป็น `รอรีวิว:` `ส่งกลับ:` และ `ถาม:` ไม่แก้ไฟล์และไม่ลงมือ

## `/tek-do-card`

### หยิบ

1. เปิด `card-loop/board.md`
2. ใช้เงื่อนไขแรกที่ตรง
   - มี `- [ ]` ที่บรรทัดเป็น `ส่งกลับ:` และ `สถานะรอบ` ใน plan ยังไม่ใช่ `ส่งกลับ` → ตั้ง `รอบหลักฐาน` เป็น 1 ตั้ง `สถานะรอบ` เป็น `ส่งกลับ` commit ที่ `card-loop/` แล้วทำข้อนี้ต่อ
   - มี `- [ ]` ที่บรรทัดเป็น `ส่งกลับ:` และ `สถานะรอบ` เป็น `ส่งกลับ` อยู่แล้ว → ทำต่อโดยไม่รีเซ็ตรอบ
   - มี `- [ ]` ที่บรรทัดเป็น `รอรีวิว:` → หยุด คนจะเรียก `/tek-open-review` เอง
3. ทุกบรรทัดที่ยัง `- [ ]` และมี `ถาม:` ให้อ่าน card
   - หัว **ถาม** ว่าง และเจตนาปิดแล้ว → ลบ `ถาม:` ออกจากบรรทัด แล้ว commit ที่ `card-loop/`
   - หัว **ถาม** ยังมีคำถาม → หยุด
4. ขั้นก่อนหน้าสั่งให้หยุดหรือทำต่อข้อเดิมแล้ว จบการหยิบ
5. นอกนั้นหยิบข้อ `- [ ]` ที่ไม่มี `ถาม:` `รอรีวิว:` หรือ `ส่งกลับ:` และมีไฟล์ card ตามลำดับ **ทำก่อน** แล้ว **งานหลัก** แล้ว **เก็บเล็ก** บรรทัดที่เป็นหัวของข้อย่อยไม่ถูกหยิบ เมื่อข้อย่อยครบให้เขียนว่าครบที่บรรทัดหัว
6. อ่าน card เจตนายังไม่ปิด → เขียน **ถาม** ท้าย card และต่อท้ายบรรทัด commit ที่ `card-loop/` แล้วหยุด
7. เจตนาปิดแล้ว → ไปลงมือ

ของที่ card ขอไม่มีในโค้ดแล้ว ให้เขียน `ถาม:` ว่าจะปิดข้อนี้ไหม ทั้งที่ card และบรรทัด แล้ว commit ที่ `card-loop/`

เปิด skill อื่นตาม [skills.md](skills.md) ไม่เกินสองใบต่อจุด ตอนหยิบ ตอนเขียน `ถาม:` และตอนคนรับหรือปิด ไม่เปิด ใบที่ไม่มีในเครื่อง ให้เดินตามกติกานี้แล้วจดใน plan ว่าไม่เจอ ห้ามติดตั้ง skill ระหว่างหยิบข้อ

### ลงมือ

branch แยกจากสาขาหลัก plan อยู่ที่ `card-loop/plan/<id>.md` จาก [assets/plan.template.md](../assets/plan.template.md)

- `feat` / `fix` เขียนเทสของพฤติกรรมนั้นให้แดงเพราะ assertion ยังไม่จริง แล้วทำให้เขียว
- `test` เทสที่เพิ่มเขียว โดยไม่เปลี่ยนพฤติกรรมผลิตเพื่อให้ผ่าน
- `fix` ที่ผู้ใช้เห็นจอ บันทึกขั้นตอนที่ทำให้บั๊กเกิด แล้วขั้นตอนเดิมหลังแก้ต้องไม่เกิด
- ไฟล์นอก **ไฟล์ที่แตะได้** ใน plan ห้ามแก้
- งานที่ย้อนกลับไม่ได้ → **ถาม** แล้วหยุด
- หลักฐานไม่ผ่านทั้งชุด → ทำตามหัว **เกณฑ์ 3 รอบ**

ก่อนเปิดของให้ review รันคำสั่งของ repo นี้จากตารางบน board

- `<TEST_CMD>` ในขอบเขตไฟล์ที่เปลี่ยน ว่างได้เฉพาะชนิดที่ไม่ใช่ `feat` หรือ `fix`
- `<TYPECHECK_CMD>` ถ้าแตะไฟล์ที่ type ครอบ และช่องนี้ไม่ว่าง
- `<LINT_CMD>` เช่นกัน
- แตะ UI และ `<BROWSER_TOOL>` ไม่ว่าง ให้ไล่เส้นที่เปลี่ยน รวมหน้าอื่นที่อ่าน state เดียวกัน และ empty, error, ตัวแปร route, ขนาดจอ ถ้าแตะ
- `<BROWSER_TOOL>` ว่าง และไม่ใช่ `fix` ที่ผู้ใช้เห็นจอ ให้ใส่ในของที่เปิดให้ review ว่าตรวจพื้นผิวอะไรไม่ได้

### เปิดของให้ review

เปิดของให้คน review ในแบบที่ repo นี้ใช้อยู่แล้วเมื่อหลักฐานผ่าน ถ้า repo ใช้ PR ให้เปิด PR ใบเดิมถ้ามีอยู่แล้ว ห้ามเปิดใบใหม่ของข้อเดียวกัน เนื้อที่คนดูต้องมี

- สรุป diff ว่าตรงหัว **ทำ** และไม่ล้ำหัว **ไม่ทำ**
- ผล `<TEST_CMD>` `<TYPECHECK_CMD>` `<LINT_CMD>` ที่รัน
- `fix` ที่ผู้ใช้เห็นจอ: ขั้นตอนบนพื้นผิวเดิมก่อนแก้และหลังแก้

จากนั้นแก้ `card-loop/board.md`

- ข้อยังเป็น `- [ ]`
- ต่อท้าย `รอรีวิว:` พร้อมที่อยู่ของของที่เปิดให้ดู
- ตั้ง `สถานะรอบ` ใน plan เป็น `รอรีวิว`
- ห้ามเปลี่ยนเป็น `- [x]`

อย่าหยิบข้อถัดไป commit โค้ดของข้อ แล้ว commit บรรทัด board กับ plan ที่ `card-loop/` คนละ commit ถ้าแยกกันได้

## คนเปลี่ยนคำบนบรรทัด

คนเรียก `/tek-open-review` ก่อนตัดสิน แล้วเรียกคำสั่งเดียว

- `/tek-mark-merge` เมื่อ diff ตรงหัว **ตรวจผ่านเมื่อ** และหลักฐานครบ เปลี่ยนบรรทัดเป็น `- [x]` ต่อท้าย `merge:` แล้ว merge ของที่เปิดไว้ถ้า repo นี้มีขั้นนั้น ย้ายบรรทัดไปส่วน **ปิดแล้ว** เมื่อคิวยาว
- `/tek-send-back` เมื่อไม่ครบหรือยังไม่ตรง เปลี่ยน `รอรีวิว:` เป็น `ส่งกลับ:` บนบรรทัดเดิม
- `/tek-mark-close` เมื่อไม่เอา เปลี่ยนบรรทัดเป็น `- [x]` ต่อท้าย `ปิด:` พร้อมเหตุ ปิดของที่เปิดไว้ถ้าปิดได้ แล้วย้ายบรรทัดแบบเดียวกัน

ห้ามติ๊ก `merge:` เพราะคำอธิบายดูเรียบ ทั้งที่หลักฐานไม่มีหรือ diff ไม่ตรง card

## สรุป

| ผล | ทำอะไรต่อ |
|---|---|
| เจตนาไม่ปิด | `ถาม:` ที่ card และบรรทัด คนล้างหัว **ถาม** แล้วเรียก `/tek-do-card` |
| ย้อนกลับไม่ได้ หรือครบ 3 รอบ | `ถาม:` ที่ card และบรรทัด |
| หลักฐานผ่าน | เปิดของให้ดู ต่อท้าย `รอรีวิว:` ข้อยังเป็น `- [ ]` |
| คนรับ | `/tek-mark-merge` |
| คนส่งกลับ | `/tek-send-back` แล้ว `/tek-do-card` |
| คนไม่เอา | `/tek-mark-close` |
