# Security

## Reporting a vulnerability

Please report suspected vulnerabilities privately through GitHub: **Security tab → Report a vulnerability** on this repository. Do not open a public issue for an unfixed vulnerability.

## Trust model (read before installing)

`jtek-skill` is not a sandbox. `jtek.py check` runs commands on your machine, and so does `jtek.py start`, which runs the same checks once on the base before any edit.

- **Which commands:** only the checks, the `setup` command, and the `pr_state` command in this machine's config for the repository (`~/.jtek/repos/<repo id>/jtek.json`, or `~/.jtek/config` when that file is absent). The script does not read `jtek.json` from the repository, so a commit cannot change a check. Whoever can write `~/.jtek` chooses the commands. `JTEK_HOME` overrides `~/.jtek`.
- **How they run:** each command is split into a program and arguments and run without a shell, in the ticket's worktree, with your full environment (including any tokens in it). The time limit is 30 minutes per check. The `pr_state` command is the exception: it runs in the main checkout, not in a worktree, with a limit of 60 seconds.
- **What a ticket can do:** name checks that `jtek.json` already declares. A name that is not declared is refused. Ticket text is read from a local file and is never executed. The script reads header lines only right under the title, up to the first blank line or line of other text. For `--local` tickets written by the session, header lines grant nothing (`review:`, `checks:`, and `after:` are ignored).
- **One more command, only when asked:** `jtek.py doctor --agents` looks for the coding agents it knows on your PATH and runs `cursor-agent --list-models` when that program is there, without a shell, with a limit of 30 seconds. It runs no other agent. `jtek.py reviewer` reads `~/.jtek/agents.json` (or `~/.config/jtek/agents.json` when only the old file exists) and prints a command from it; the script never runs that command. The session that reads the line does, so review that file as you review a shell profile: whoever can write it chooses what a session starts. `jtek.py guess` reads package manifests and CI `run:` lines only, skips dotenv files, and prints a command only when it matches a fixed shape. `jtek.py status` only reads.
- **Treat the machine config like CI config.** It is not in the pull request. Review it on the machine that runs the checks. A committed `jtek.json` or `.jtek/` is named on the `attention:` line because those paths no longer configure jtek.
- **The `verify` script is code too.** The `jt-harness` skill writes the guide under `~/.jtek/repos/<repo id>/` and one script in the repository. The machine config names that script, but the script itself is read from the ticket's worktree, so a ticket can change it. Review changes to it, and to anything a check runs, as you review product code. The result's `attention:` line names such a file when a ticket changes it, along with a committed `jtek.json`, `.jtek/`, or `.claude/*`, CI config, lockfiles, files such as `Makefile` and `package.json`, and deleted or shortened tests. It works from a list of known names plus your `watch` patterns, so a file the list does not know is not named. It is a pointer for the reviewer, and it only blocks the `review: human` waiver.

## What the script cannot enforce

- It records the session that ran `start`, and every later `start` of that ticket, and `verdict` refuses the same session. Set `JTEK_SESSION`, or `CURSOR_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`, or `CODEX_THREAD_ID`. The hash is of that text only, so the same text under any of those names is the same session. There is no parent-process id: a second shell would share it and could record a pass. `start` and `verdict` refuse when none of those names is set. Only a short hash is stored. The value is never printed. The authors list is sealed with a key in the state directory (`author.key`). A hand edit of `meta.json` that does not recompute the seal is refused. A process that can rewrite both the key and `meta.json` can still forge the list. The list keeps at most 20 ids, and the original writer is never the one dropped. An agent that sets a different `JTEK_SESSION` for the verdict can still bypass this. Do not put `jtek.py release` or `jtek.py verdict` on an always-allow list in the session that writes code. An agent can still commit to the base branch or edit a local ticket file to `status: Todo` on disk. The skills forbid both.
- It trusts what the session passes in: the header lines of a non-local ticket file, `--resume`, `--no-baseline`, and the `JTEK_BASE`, `JTEK_STATE`, `JTEK_HOME`, and `JTEK_SESSION` variables. Its state is plain files under the git directory. `finish --no-pr` with a remote is allowed only when this machine's config has `"forge": false`. A commit cannot set that flag: not the published base, not an unmerged branch, and not a replace ref. `init` and `start` seal the configured origin URL (`remote.origin.url`, not the `insteadOf` expansion) with the same key. A missing, empty, or damaged seal is not written again by a later `start`. `finish --no-pr` is refused when that seal is missing or does not match, when the configured URL is not the sealed one, or when a `url.*.insteadOf` rule would send `ls-remote` and `fetch` to a different repository. A rewrite that keeps the same repository, such as a credential on `https://github.com/`, does not refuse. A sealed empty URL means no origin existed yet. A process that can rewrite both the key and that state can still forge the seal. The same limit covers the authors list and `broke.json`: possession of the key and the state files is enough to recompute every seal. Whoever can write `~/.jtek` can set `forge` to false; that is the same user who can edit the script. A token in a `--pr` link is redacted before it is printed. `show --at` on a fast-forward does not trust `refs/remotes/origin/<base>`. It uses the reflog, or the sha `git ls-remote` reports when that sha covers more than the last commit. A remote tip one commit behind is refused, so a longer fast-forward is not reviewed as only the last commit.
- It does not prove the model the reviewer list names. `verdict --by` is a label, and so are `vendor` and `model` in `agents.json`.
- It does not check that the evidence is true. The evidence is the author's account, written for the human to read first. The checks and the reviewer's own runs are what test the change.
- `finish` requires a `broke` record for every `Done when` item. The script itself ran a declared behaviour check while the worktree was dirty and saw it fail, then the author restored the file. The record is sealed with the same key as the authors list. A hand-written `broke.json` does not count. It does not judge whether that edit was the behaviour the item names. A check that still passes is not a record. A lint, format, or type check is not a record either, including when its name is `eslint`, `ruff-format`, `bandit`, `semgrep`, `shellcheck`, `hadolint`, `stylelint`, or `markdownlint` rather than `lint`.

## What the skills do outside the repository

- **Worktrees:** `start` creates `.claude/worktrees/<id>` inside the repository (and adds `.claude/worktrees/` to `.git/info/exclude` once, without editing tracked files) and the branch `jtek/<id>`. Existing claims keep the path stored in `meta.json`.
- **State:** a copy of each ticket, claims, check logs, review notes, and results are under `<git-common-dir>/jtek/` and are not committed. Check logs can contain secrets that a command printed.
- **Ticket files:** `ticket --save` writes `~/.jtek/repos/<repo id>/tickets/<id>.md` on this machine, and `start`, `stop`, `finish`, and `sync` update the `status:`, `waiting:`, and `pr:` header lines in regular (non-symlink) ticket files atomically. Nothing is committed. Files already in `<repo>.jtek/_tickets` are still read. A new machine does not have the folder until you copy it or run `jtek.py migrate` there.
- **Network:** the script calls `gh pr view` / `gh pr ready` (or `glab mr view` / `glab mr update --ready` on GitLab) in `finish` and `sync`, or the `pr_state` command when the project set one. `jtek.py comment` calls `gh pr comment` (with `gh api` issue-comment fallback when denied) or `glab mr note`. `show` and `verdict` may `git fetch` `refs/pull/<n>/head` when that ref is not already local. `cursor-agent --list-models`, run by `doctor --agents`, asks that program's own service. Nothing else.
- **Push:** the `jt-ship` skill tells the agent to push the ticket branch and open a pull request. This sends your code to that remote on purpose.
- **Merge:** never. There is no command for it.
